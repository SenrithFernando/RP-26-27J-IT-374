# Stage 6 — synthetic-data XGBoost pipeline

**This demonstrates a synthetic-data ML pipeline. Real-world accuracy has not yet been established.**

The project had no existing ML implementation. The new code uses the existing Python environment and travel-cost validation interface. Legacy simulation endpoints remain available. The frontend retains its layout and renders Python-generated results; it does not train or predict in the browser.

```powershell

Packages were already installed locally: XGBoost 3.4.1, NumPy 2.5.4 and scikit-learn 1.9.1. `pip check` passed.

## Dataset and feature contract

`data/travel_times_synthetic.csv` was generated by running the script. It contains **2,000 observations, 400 five-segment trips, eight weeks and 22 source locations**, with seed `20261015`. SHA-256: `e34925aad5b34d5d51c6f632a64b2a09d7ee4bfca057e8a789c9f43061a1814a`.

Every row has `data_source=synthetic`. Location provenance is retained separately in `travel_times_synthetic.locations.json`; source coordinates do not turn generated duration targets into measured observations. The manifest records seed, counts, checksum and target recipe. There are no measured road times, traffic API observations or real weather observations in this dataset.

Required CSV columns are `trip_id`, `origin_id`, `destination_id`, `departure_timestamp`, `distance_m`, `hour`, `day_of_week`, `weather_flag`, `duration_s`, `data_source`. Stable routing location IDs identify directed segments. The internal segment key is a JSON-encoded ordered pair, avoiding delimiter collisions. Distances are approximate haversine straight-line metres. Generated local arcs range from 25 to 30,000 metres. The generator uses nonlinear morning/afternoon peaks, stable directed-segment differences, weekday effects, weather interactions and lognormal noise. Some weather inputs are deliberately absent while the synthetic target still includes latent weather effects.

The shared prediction-time feature schema is saved in model metadata and `docs/ml_metrics.json`:

- Numerical: straight-line distance, local fractional hour, weekday (Monday 0), weather flag, weather-missing indicator.
- Categorical: origin ID, destination ID and directed segment ID; fitted one-hot vocabularies are JSON, not executable pickle files.
- Missing weather: `null` in the API or an empty CSV field becomes `-1` plus missing indicator 1. No weather forecast is fetched or silently assumed dry.
- Unknown categories: all-zero encoding for the unknown field; known numerical/ID features still contribute. Responses disclose unknown segments and extrapolation beyond the training distance range. Weekends are outside this weekday development population and are explicitly flagged.
- Target: `log(duration_s)` during fitting; inverse exponential produces positive durations. Nonfinite/nonpositive predictions are rejected.
- Excluded: target duration, trip ID, future arrival, route completion, synthetic provenance and other unavailable target-derived information.

`POST /ml/predict` accepts an offset-aware departure timestamp and derives clock features on the backend in Asia/Colombo. It rejects invalid distance, weather, naive timestamps and unexpected fields. Distance is a supplied prediction-time input using the same straight-line feature definition; this endpoint is not a road-distance provider.

## Chronological evaluation

Four expanding-window walk-forward folds train on earlier complete weekly blocks and validate on the next week. Trips remain together, and the trainer checks that training and evaluation time ranges do not overlap. Every fold fits categorical preprocessing and historical averages from that fold's training rows only. The baseline is the directed segment's training-only mean duration; unseen segments fall back to the training-only global mean duration.

XGBoost parameters are fixed in source before final testing: 240 trees, depth 4, learning rate 0.045, histogram trees, seed 20261015, one CPU worker. There is no parameter search or early stopping on the final test. The published model is fitted on development rows only; it is not refitted using the final-test targets.

| Split | Training observations | Evaluation observations | Evaluation local time range |
|---|---:|---:|---|
| Walk-forward 1 | 500 | 250 | Week beginning 2026-07-20 |
| Walk-forward 2 | 750 | 250 | Week beginning 2026-07-27 |
| Walk-forward 3 | 1,000 | 250 | Week beginning 2026-08-03 |
| Walk-forward 4 | 1,250 | 250 | Week beginning 2026-08-10 |
| Untouched final test | 1,500 / 300 trips | 500 / 100 trips | 2026-08-17 05:42:52 through 2026-08-28 16:36:09 +05:30 |

Final development training range: **2026-07-06 05:43:42 through 2026-08-14 16:40:39 +05:30**. Exact timestamp ranges for every fold, counts, missing-weather and unseen-segment subgroup scores are in the generated metrics JSON.

## Artifacts and status

`backend/ml/artifacts/current.json` selects a versioned directory containing:

```text
model.json          XGBoost save_model output
preprocessing.json  Training-only categorical vocabularies and schema version
baseline.json       Training-only segment averages and fallback
metadata.json       Model version, schema, provenance, ranges, library versions, checksums
metrics.json        Actual evaluation output, matching docs/ml_metrics.json
```

The loader checks file hashes and schema/model versions before exposing inference. No credentials or database URLs appear in these files. Serialization uses XGBoost's supported JSON model format ([official model IO documentation](https://xgboost.readthedocs.io/en/stable/tutorials/saving_model.html)). The chronological approach follows the time-ordering principle explained in [scikit-learn's time-series validation documentation](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.TimeSeriesSplit.html); the implementation groups whole trips into weeks instead of splitting individual rows.

```powershell
Invoke-RestMethod http://127.0.0.1:8000/ml/status
$prediction = @{
    origin_id = 'S4_HOME_01'
    destination_id = 'S4_SCHOOL_A'
    departure_timestamp = '2026-10-15T07:30:00+05:30'
    distance_m = 1500
    weather_flag = $null
} | ConvertTo-Json
Invoke-RestMethod http://127.0.0.1:8000/ml/predict -Method Post -ContentType 'application/json' -Body $prediction
```

The example above supplies a hypothetical 1,500-metre distance; responses disclose the exact feature values used. For a demonstration with current confirmed geometry, run the command below. It selects an assigned student and calculates the example distance from current coordinates.

The existing independent solver audit checks coverage, registered assignment, pickup precedence, destination, deadlines, school finish times, capacity and time accounting before saving a feasible result. Capacity is 2 for this six-student multi-school fixture; students are not moved to other vehicles. Feasibility is based on model-predicted travel costs, not a guarantee about real travel.

The ML provider builds and validates all pairwise costs before OR-Tools callbacks. Durations are model predictions rounded upward to whole seconds. Diagonal/colocated arcs have zero geographic travel, while configured service time stays separate. Distance remains straight-line approximation. All arcs use the vehicle's configured departure timestamp in a **static matrix**, not estimated future arc departure times. This is not a live or time-dependent traffic provider. Unknown segments are supported and flagged; a missing model rejects generation without falling back to simulation. Stage 5 regeneration reuses the saved provider/weather settings.

Manual generation remains:

```powershell
$route = @{
    vehicle_id = 'S4_VAN_A'
    direction = 'morning'
    departure_seconds = 21600
    provider = 'ml'
    weather_flag = $null
    solver_time_limit_seconds = 2
} | ConvertTo-Json
Invoke-RestMethod http://127.0.0.1:8000/routes/generate -Method Post -ContentType 'application/json' -Body $route
```

`simulation_speed_mps` must be omitted or null for ML. Existing requests that omit `provider` retain deterministic simulation. GET latest remains read-only. Existing pre-trip execution guards still prevent reordering active/completed execution snapshots. Switching providers changes the cost assumptions; a difference between provider estimates is not measured journey savings.
