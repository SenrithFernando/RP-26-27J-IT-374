Traffic generation now supports deterministic directed-edge scenarios, Google Routes traffic-aware input, loaded XGBoost predictions, an explicit historical baseline and an explicit unavailable result. Source selection happens on the backend before OR-Tools is constructed. Existing route endpoints and Stage 5 mutation orchestration remain operational.

**PP1 uses one departure-time matrix snapshot for every arc. This is not a fully time-dependent solver.** Later arrival at a stop does not trigger another matrix request or change arc costs during search. Google traffic-aware values are provider estimates; ML predictions and simulation are not measured observations.

## Provider controls and source rules

`POST /routes/generate` accepts these additional settings; old requests retain their defaults:

| Field | Values / behavior |
|---|---|
| `provider` | `simulation`, `google`, `ml`, `baseline`, `unavailable` |
| `traffic_scenario` | `normal`, `northbound_delay`, `directed_incident`; synthetic scenarios require simulation |
| `fallback_policy` | `none`, `ml`, `ml_then_baseline`; default `ml` |
| `force_live_failure` | Google-only local demonstration switch; bypasses cache and makes no external call |
| `include_geometry` | Requests ordered road geometry for successful Google-backed routes; default true |
| `weather_flag` | User planning input 0/1, or null for missing; never a silently fetched weather observation |

`simulation_speed_mps` must be omitted or null except with simulation. Synthetic traffic scenarios are not applied to Google values or injected into the ML model as an untrained feature. API validation rejects that combination.

Simulation modifies a subset of directed edges:

- `northbound_delay`: arcs travelling north across the roster's median-latitude corridor get `ceil(base_seconds × 1.8) + 120` seconds. Reverse and unaffected arcs retain base costs.
- `directed_incident`: a stable hash of the directed location-ID pair selects approximately one fifth of nonzero arcs; selected arcs get `ceil(base_seconds × 2.5) + 180` seconds. Reverse directions are selected independently.
- `normal`: no added scenario delay. A scenario can legitimately affect no useful route legs; stop orders are not forced to change.

The snapshot records scenario name, modified directed matrix arc count and a content-based matrix ID. Distances stay unchanged for simulated congestion. All scenario inputs/outputs are labelled simulation, not live traffic.

Google failures fill only failed/omitted pairs through the selected chain:

```text
Google success → Google duration + Google road distance
Google transient/missing input → loaded ML + approximate straight-line distance
ML unavailable + explicitly selected ml_then_baseline → historical baseline
No permitted estimate → unavailable
Google authoritative ROUTE_NOT_FOUND → unavailable (no ML/baseline reachability claim)
```

`none` disables fallback. Selecting ML directly can use baseline only if `ml_then_baseline` is selected. Baseline reads a verified Stage 6 historical-average artifact independently of the XGBoost loader, so the baseline can remain available even when model inference is unavailable. Its unseen-segment fallback is the training-only global average, labelled explicitly. Missing baseline artifacts also return unavailable. No fixed ETA or fabricated distance is used.

Every stored stop has `travel_source` for its incoming leg: actual source, distance source, model version where applicable, synthetic training provenance, scenario modification, failure code and fallback/unavailable reason. Colocated legs are explicitly zero geographic travel, with separate service time. Nonzero selected route legs determine the route's source label; routes using more than one source are **mixed**. Matrix-wide and selected-route source counts remain separate. A route using only ML fallback is labelled ML, even if unused matrix entries had live values.

## Live adapter bounds and failures

The adapter uses Google's `computeRouteMatrix` with `DRIVE`, `TRAFFIC_AWARE`, offset-aware future departure, and a field mask including indices, status, condition, distance and duration. It deduplicates physical coordinates, batches at most 10 origins × 10 destinations, and caps a live snapshot at 40 unique locations. Larger snapshots use the selected fallback rather than issuing unbounded requests.

The socket timeout defaults to 4 seconds (bounded to 0.1–10); the matrix request budget defaults to 12 seconds (bounded to 0.1–30). Remaining budget is checked between batches and limits subsequent request timeouts. There are no automatic retry loops. A bounded in-memory LRU stores at most 32 fully validated successful chunks for 60 seconds. Cache keys include coordinates, exact departure, routing preference and a credential fingerprint; keys themselves are never exposed. Hits do not renew entry lifetime. Partial/failed chunks are not cached. Forced failure bypasses both cache and transport.

HTTP 429 and element status 8 are quota failures; 401/403 identify credential rejection. Network/timeouts, malformed values, duplicate indices, missing elements and unknown conditions have explicit failure codes. Missing entries are never assigned zero duration. The requested departure is never silently changed to now if it is in the past. Known unreachable pairs reject generation; unknown transient failures can use labelled estimates.

See the primary [Google matrix API reference](https://developers.google.com/maps/documentation/routes/reference/rest/v2/TopLevel/computeRouteMatrix) and [traffic-aware request guidance](https://developers.google.com/maps/documentation/routes/config_trade_offs). This adapter uses a more conservative batch limit than Google's maximum.

## Fair route alternatives

For a feasible selected solution, the backend evaluates a reference stop order against the **same in-memory matrix**, departure, service times, roster and time windows used by the solver. It uses the previous stop order when its event IDs match the current roster; otherwise it uses the registered-student sequence, with each student's pickup then delivery. It never reuses the previous route's driving costs or ETAs.

The reference receives a fresh schedule, waiting calculations, load/coverage/destination audit and feasibility check. An infeasible reference is identified with its constraints and unavailable comparison metrics. A feasible comparison records reference and selected values, `reference_minus_selected`, whether the sequence changed, and the matrix ID. Zero and negative differences remain visible. Historical before/after results remain separately labelled as historical changes, not optimization savings.

Actual local corridor demonstration, matrix **`dc1d7d7ae3054d79d40bfefc`**, modified **49 directed action arcs**:

| Selected corridor solution | 3,124 | 360 | 3,484 |
| Reference minus selected | 583 | 0 | 583 |

The old normal-traffic driving value of 2,414 seconds is **not** the comparison denominator. The 583-second difference compares two estimated stop orders under the same simulated corridor costs; it is not measured journey savings or proof of a global optimum. The forced-failure morning demonstration subsequently retained the same 2,622-second driving result as its repriced reference, with **zero** deltas and unchanged stop order.

## Road geometry

When successful live legs are selected, the adapter can call `computeRoutes` once after solving, preserving the exact ordered stops (`optimizeWaypointOrder=false`). It requests an encoded road polyline and does not replace the optimizer's snapshot estimates with the geometry request's timing. The prototype limits this request to 25 intermediate stops. If all live values failed, it does not issue another geometry request. Forced failure also disables geometry without transport calls.

Google's [display policy](https://developers.google.com/maps/documentation/routes/policies) requires its map data to be shown on a Google Map. The optional `/routes/{route_id}/map-image` endpoint therefore proxies a Google Static Maps image with the returned path; its key remains on the backend and the image retains Google's attribution. The image cache is bounded to eight images, 60 seconds and 2 MB per image; browser responses use `Cache-Control: no-store`. If the Static Maps key/API or image is unavailable, the frontend clearly falls back to the existing Leaflet confirmed-location/stop-sequence display. Google road polylines are not drawn over OpenStreetMap tiles.

Simulation, ML and baseline do not invent roads. Without usable road geometry/display the map keeps **“Stop sequence — not a road route”**. OpenStreetMap remains a basemap, not the routing/traffic provider. Actual live geometry was blocked locally by the absent credentials; contract and order preservation were tested with mock geometry only. Provider data retention/display must follow the applicable Google agreement for deployment; the research prototype retains planning versions in PostgreSQL and does not claim a production licensing review.

1. Open http://localhost:5173 → **Administrator → Routes → S4_VAN_A** (or a suitable registered vehicle).
2. Choose **Deterministic simulated traffic**, select **Normal simulation**, and generate. Then choose **Northbound corridor delay** or **Selected directed-edge incidents**, and generate. 3. Choose **Google traffic-aware (with explicit fallback)**. The page explicitly states when Google is not configured. Choose **ML only; otherwise unavailable**, tick **Force live adapter failure**, and generate. Inspect the actual **ML-predicted driving**, model version, per-stop source badges and fallback reason. Test both directions.
4. Select **No fallback; show unavailable** while keeping forced failure enabled, then generate. There must be no working itinerary or available ETA/distance. A stored older itinerary must not appear current.
5. Select **Historical average baseline** and generate to inspect baseline labelling. Select **Unavailable (no estimate)** to inspect the explicit unavailable state.
6. If real Google credentials become available, choose a **future** service date/departure, turn forced failure off, choose the desired fallback and generate. Only successful Google legs may be labelled Google; partial fallback routes show **Mixed sources** when both sources are actually used. Road geometry/display requires the respective enabled APIs and backend keys.
7. Reload the stored route. Reads do not generate a new version. Input mutations continue to regenerate the two affected pre-trip plans using saved provider/scenario settings, with active/completed execution guards preserved.
